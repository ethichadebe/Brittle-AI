# 2026-10-01 — Remember a Shopper's Substitute decisions

- **Asked for:** #91, re-grilled first against how compare behaves now that
  low-confidence matches come back as Suggestions (#102). The grilling
  changed the issue's acceptance criteria and split crowd promotion out
  into #103.
- **Worked first time:** yes, against the agreed criteria.
- **Laptop needed:** no.
- **Friction:**

  - **Grilling before building paid off.** The issue was written before a
    shopper could pick a Suggestion, so "accepted" had two meanings. Settling
    the language first (`CONTEXT.md`: a picked **Suggestion** is a
    **Substitute**; only deliberate taps are remembered) left one decision
    per pairing to store, instead of two parallel mechanisms. Crowd
    promotion came up mid-grilling and contradicts #91's own "a preference,
    not a fact" premise, so it went to #103 rather than in here.

  - **No store can be asked for a product by id.** A remembered pick is
    found again by searching for its own name (the same trick
    `priceCache.refreshItems` already uses), which is why the decision
    stores the Substitute's name as well as its id. Searching for the pick
    *instead of* the list item keeps it to one search when the pick is
    still there; when it's gone, matching falls back to normal at the cost
    of a second search. The tradeoff, agreed while grilling: a remembered
    pick stops Accucery looking for anything better until it's unticked.

  - **Two small calls made without asking**, both following from what was
    agreed rather than adding to it:
    - Un-picking a Suggestion *forgets* the pick. The grilling said
      un-picking records nothing, but leaving the earlier "chosen" in place
      would have auto-applied a mistaken tap on the next comparison.
    - A new pick for an item replaces any older pick for the same item at
      that store. Two remembered picks would leave no way to say which to
      apply; this can only happen when the old pick stopped being sold and
      the shopper picked a Suggestion instead.

  - **First session with a local Postgres.** Installed via apt, so the
    migration was generated by `prisma migrate dev --create-only` rather
    than by hand, and the `*.db.test.ts` suite ran here for the first time
    in this session: 61 passing, 9 of them new. The migration is
    `CREATE TABLE` plus a foreign key, which the deploy gate treats as
    additive. Removing the Account removes its decisions (`ON DELETE
    CASCADE`), for when #88 adds account deletion.

  - **Checked in a browser, against canned API responses.** The cloud
    session can't reach the stores, so the frontend dev server ran with
    every `/api` call answered by Playwright, and the script recorded the
    decision requests each tap sent: untick → `PUT removed`, re-tick →
    `DELETE`, pick → `PUT chosen`, un-pick → `DELETE`, Undo → `DELETE` then
    a fresh comparison. This proves the wiring, not the matching. The real
    check is still a live list.

  - **Next:** live-test on a list compared twice. #103 (crowd promotion)
    needs its own grilling before anything is built.
